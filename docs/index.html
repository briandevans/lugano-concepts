Failure atlas

Private AI fails at the boundaries.

The model is only one privacy actor. A serious documentation center shows the whole path, including tools, metadata, observability, and runtime operations.

Layer What can leak Common failure Control question
Client and browser Prompt text, files, screenshots, cookies, local storage, extension access. The server is private, but the browser plugin or local cache keeps sensitive content. What does the client store, and which extensions or scripts can see it?
Identity and access Names, emails, tenant ids, API keys, IP addresses, device ids, billing events. Content is protected, but identity and metadata still reveal business intent. Can identity be separated from content where it is not needed?
Prompt routing Raw prompts, model choices, policy decisions, gateway traces, retry queues. A gateway logs the full request while promising the downstream model has no retention. Which component first sees plaintext and which records prove minimization?
Tool calls Tool arguments, outputs, screenshots, URLs, repository names, CRM records, emails. Private model inference is followed by a third-party search, browser, or MCP call. Are tool arguments scoped, approved, and logged with the same privacy boundary?
RAG and files Documents, chunks, embeddings, OCR text, previews, citations, deleted records. Embeddings outlive source documents or cross tenant/workspace boundaries. How are ingestion, retrieval, deletion, and authorization tied together?
Model runtime Inputs, outputs, KV cache, batch neighbors, provider telemetry, crash dumps. A model route is private in policy, but the runtime has unmanaged debug visibility. What evidence identifies the runtime, route, and active policy for a request?
Observability Traces, errors, analytics events, session replays, performance counters, support exports. Plaintext is redacted in one log but copied into another system for debugging. Which logs are content-aware, and who can access them?
Hardware boundary Host memory, accelerator paths, attestation details, firmware state, side channels. A hardware privacy claim is made without naming what it covers or excludes. What is measured, who verifies it, and where does plaintext exist outside it?
Audit artifacts Receipts, commitments, policy ids, timestamps, disclosure bundles, verifier results. The system says it was private, but cannot produce request-specific evidence later. Can a reviewer independently check the claim without seeing the secret content?

Foundations

AI Privacy Threat Model

A practical map of the people, systems, and logs that can see an AI request.

Security leaders

Privacy starts before the model

An AI request can cross a browser, identity provider, gateway, orchestration runtime, model endpoint, storage layer, analytics system, and observability stack. A vendor can protect one layer and still leak sensitive data through another.

The stronger question is not only whether the model provider trains on your data. Ask who can observe the path, which systems retain it, which operators can replay it, and what evidence proves those answers later.

Working definition

AI privacy means minimizing plaintext exposure, separating identity from content where possible, and producing evidence for the parts of the path that were controlled.

Failure points

Prompt and Response Retention

How content survives in chat history, provider logs, queues, transcripts, and support tooling.

Data protection

Retention is broader than training

A provider may exclude prompts from training while still retaining request payloads for abuse monitoring, debugging, billing disputes, quality review, latency analysis, or incident response. Those systems can be reasonable, but they are still exposure surfaces.

Applications can also create copies before a request reaches the model: transcripts, retry queues, traces, customer support exports, webhooks, background jobs, browser storage, and crash reports.

Common failure

A product says prompts are not used for training, but the same plaintext is stored in analytics or support exports.

Failure points

Tool Calls and Agent Actions

Why private inference is incomplete when plugins, MCP servers, browsers, and actions expose data.

Agent builders

Tools expand the blast radius

A model answer may be private while the tool call that enabled it is not. Agents can send sensitive arguments to search providers, ticketing systems, shell commands, hosted browsers, email APIs, calendars, wallets, databases, MCP servers, or custom plugins.

Every tool should have an allowlist, scope, approval rule, data minimization policy, and logging policy. High-risk tools should record what was approved before execution.

Agent privacy trap

A workflow routes chat through a private model, then sends the same confidential facts to a third-party scraper.

Failure points

RAG, Files, and Vector Databases

How retrieval leaks through ingestion, embeddings, chunk stores, search indexes, and previews.

Workspace teams

The document path is a second data plane

Retrieval adds upload, parsing, OCR, chunking, embedding, indexing, ranking, and citation rendering. Each stage can store plaintext, derived text, metadata, or previews.

Embeddings are not a substitute for access control. They can encode sensitive semantics, expose document membership, and persist after the source file is deleted unless index lifecycle is explicit.

Failure points

Identity, Metadata, and Analytics

How privacy can fail even when prompt text is minimized or encrypted.

Product teams

Metadata tells a story

Tenant id, user id, IP address, timestamps, model ids, document names, tool names, token counts, error classes, and billing events can reveal what a team is doing. In regulated or competitive settings, that context can be sensitive.

Better systems avoid joining identity and content by default, reduce unnecessary analytics, and give reviewers a clear map of which metadata exists and why.

Failure points

Observability and Support Access

How traces, session replay, employee access, and incident tooling can become the privacy boundary.

Operators

Debuggability creates copies

Logs, traces, metrics, dashboards, session replay, and support tooling are built to make systems understandable. That is useful, but AI workloads often place sensitive content exactly where debugging tools want detail.

Strong operations programs use redaction before telemetry, break-glass workflows, role-scoped access, retention limits, immutable access records, and customer-visible evidence for support actions.

Control layers

Hardware Privacy and TEEs

What hardware-backed privacy can prove, and where software, networking, and operations still matter.

Infrastructure teams

Hardware is a boundary, not the whole system

Trusted execution environments, measured boot, secure enclaves, HSMs, TPMs, and accelerator isolation can reduce operator visibility and produce useful evidence. They do not automatically solve client leakage, tool leakage, storage retention, or support access.

Ask what is measured, who verifies the measurement, where keys are released, what plaintext exists outside the boundary, and which claims are request-specific rather than generic architecture descriptions.

Control layers

Local and Edge Device Privacy

Why local processing helps, and why device logs, sync, extensions, and malware still matter.

Device teams

Local is not automatically private

Local inference or pre-processing can keep data away from cloud providers, but the device becomes part of the trusted boundary. Clipboard history, browser extensions, crash reports, sync services, endpoint monitoring, and local malware can still observe sensitive material.

Practical controls include local redaction, explicit file handling, secure storage defaults, extension isolation, managed update channels, and clear user-visible state for what leaves the device.

Control layers

Network and Browser Boundaries

How DNS, proxies, browser extensions, web search, and remote browsing create observability.

Security engineers

The network sees patterns

DNS lookups, SNI, IP addresses, request timing, proxy logs, browser automation, and web search queries can reveal intent even when payload content is protected. Agentic browsing makes this sharper because the system may visit URLs on behalf of the user.

Reviewers should ask which network intermediaries exist, whether browser sessions are isolated, how cookies and credentials are handled, and whether web search is treated as an external disclosure.

Verification

Vendor Procurement Checklist

A practical review sequence for private AI claims without asking for proprietary internals.

Buyers

Ask for scoped artifacts

Start with a data-flow diagram, then ask which systems see plaintext, which systems retain content, which subprocessors are involved, which employees can access records, and which artifact proves a request used the approved route.

A mature vendor can explain claim scope without exposing protected implementation details. The answer should distinguish product policy, software controls, hardware boundaries, logging behavior, key custody, and review evidence.

Verification

Verification Artifacts and Audit Records

What serious privacy claims should let a reviewer check after the fact.

Auditors

Evidence should survive the request

Stronger systems bind request id, route id, policy version, model id, timestamp, retention posture, and verification result into a record that can be checked later. The record should not require exposing the raw secret content to prove the claim.

The best evidence is narrow and useful: it tells a reviewer exactly what was controlled, what was not claimed, and which independent checks are available.

Documentation posture

Public documentation can educate reviewers on the shape of evidence without revealing private production mechanics.

Control layers

Control layers and evidence.

Strong privacy documentation separates software policy, runtime placement, tool governance, storage behavior, and verification records.

SW

Software policy

Admission rules, model allowlists, tool permissions, retention limits, and redaction paths should be explicit.

HW

Hardware boundary

Hardware claims should name what is measured, where keys are released, and what remains outside the boundary.

ID

Identity separation

Systems should avoid joining user identity and sensitive content unless the workflow truly requires it.

TL

Telemetry minimization

Observability should collect the least sensitive detail that still lets operators keep the service reliable.

TO

Tool governance

Agent tools should be scoped, approved, logged, and reviewed as first-class privacy boundaries.

AU

Audit records

Evidence should be request-specific enough to be useful without forcing reviewers to see secret inputs.

Glossary

Terminology.

Plaintext exposure

Any point where sensitive content exists in readable form for software, operators, logs, or external tools.

Retention

The period and surface where content, metadata, derived records, or backups remain after a request completes.

Tool boundary

The approval, execution, logging, and vendor surface around an agent action outside the core model call.

Attestation

Evidence that a measured runtime or hardware-backed environment matched an expected state at a point in time.

Commitment

A cryptographic reference to content or configuration that can be checked later without revealing the original secret.

Claim boundary

The exact scope of what a privacy statement covers, what evidence supports it, and what it does not cover.
