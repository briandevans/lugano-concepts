AI Privacy Documentation

AI privacy across the full request path

Learn where AI systems expose prompts, files, identity, tool arguments, compute metadata, logs, and verification records. This center is organized as a reference guide, not a marketing page or a set of collapsible previews.

Overview

A private AI architecture is only as strong as the least controlled part of the request path. The model service matters, but so do the client, application layer, tool layer, storage layer, observability stack, support workflow, and supporting records.

The documentation below teaches those surfaces directly. Each guide names a privacy failure mode, explains why it happens, and describes the type of control or artifact a serious system should be able to show.

No-training is not private AI

A setting that says prompts are not used to train future models is a model-improvement setting. It is not, by itself, a full privacy boundary.

The same prompt can still move through product history, abuse monitoring, debugging systems, support tools, analytics events, tool calls, file pipelines, queues, backups, and employee-access workflows unless each surface is separately controlled.

What the toggle usually covers
Whether customer prompts and outputs are used to improve or train future model behavior.
What it does not answer
Whether plaintext is retained, who can access it, which vendors process it, where tool calls send it, and what records survive after the request.
What to look for instead
A clear map of every system that can see sensitive content, retention limits for each surface, employee-access controls, and evidence that the stated policy was followed.

The AI request path

Privacy can fail before a request reaches the model and after a response leaves it. Read the path from left to right when evaluating a product or workflow.

  1. Client and identity Browser state, uploaded files, account metadata, IP address, and device context.
  2. Application policy Routing decisions, model selection, access rules, tenant controls, and review records.
  3. Tools and agents Function arguments, MCP servers, plugins, browsers, APIs, and intermediate outputs.
  4. Compute and storage Model host, hardware boundary, queues, caches, transcripts, vectors, and backups.
  5. Evidence and review Policy records, retention notes, evidence summaries, access records, and scoped claims.

Failure atlas

Use this table to identify where plaintext, metadata, and derived records can leave the expected privacy boundary.

Layer What can leak Common failure Control question
Client and browser Prompt text, files, screenshots, cookies, local storage, extension access. The server is private, but the browser plugin or local cache keeps sensitive content. What does the client store, and which extensions or scripts can see it?
Identity and access Names, emails, tenant ids, API keys, IP addresses, device ids, billing events. Content is protected, but identity and metadata still reveal business intent. Can identity be separated from content where it is not needed?
Prompt routing Raw prompts, model choices, policy decisions, application traces, retry queues. An application logs the full request while promising the downstream model has no retention. Which component first sees plaintext and which records prove minimization?
Tool calls Tool arguments, outputs, screenshots, URLs, repository names, CRM records, emails. Private model inference is followed by a third-party search, browser, or MCP call. Are tool arguments scoped, approved, and logged with the same privacy boundary?
RAG and files Documents, chunks, embeddings, OCR text, previews, citations, deleted records. Embeddings outlive source documents or cross tenant and workspace boundaries. How are ingestion, retrieval, deletion, and authorization tied together?
Model service Inputs, outputs, KV cache, batch neighbors, provider telemetry, crash dumps. A model service is private in policy, but the hosting environment has unmanaged debug visibility. What evidence identifies the hosting environment and active privacy policy for a request?
Observability Traces, errors, analytics events, session replays, performance counters, support exports. Plaintext is redacted in one log but copied into another system for debugging. Which logs are content-aware, and who can access them?
Hardware boundary Host memory, accelerator paths, attestation details, firmware state, side channels. A hardware privacy claim is made without naming what it covers or excludes. What is measured, who verifies it, and where does plaintext exist outside it?
Audit artifacts Request records, content references, timestamps, evidence summaries, review results. The system says it was private, but cannot produce request-specific evidence later. Can a reviewer independently check the claim without seeing the sensitive content?

Reference guides

Foundations

AI Privacy Threat Model

An AI request can cross a browser, identity provider, application layer, orchestration service, model service, storage layer, analytics system, and observability stack. A vendor can protect one layer and still leak sensitive data through another.

The better question is who can observe the request path, which systems retain it, which operators can replay it, and what evidence proves those answers after the request has completed.

Working definition

AI privacy means minimizing plaintext exposure, separating identity from content where possible, and producing evidence for the parts of the path that were controlled.

Failure points

Prompt and Response Retention

A provider may exclude prompts from training while still retaining request payloads for abuse monitoring, debugging, billing disputes, quality review, latency analysis, or incident response. Those systems can be reasonable, but they are still exposure surfaces.

Applications can also create copies before a request reaches the model: transcripts, retry queues, traces, customer support exports, webhooks, background jobs, browser storage, and crash reports.

Common failure

A product says prompts are not used for training, but the same plaintext is stored in analytics events or support exports.

Failure points

Tool Calls and Agent Actions

A model answer may be private while the tool call that enabled it is not. Agents can send sensitive arguments to search providers, ticketing systems, shell commands, hosted browsers, email APIs, calendars, wallets, databases, MCP servers, or custom plugins.

Every tool should have an allowlist, scope, approval rule, data minimization policy, and logging policy. High-risk tools should record what was approved before execution.

Agent privacy trap

A workflow uses a private model, then sends the same confidential facts to a third-party scraper or unmanaged plugin.

Failure points

RAG, Files, and Vector Databases

Retrieval adds upload, parsing, OCR, chunking, embedding, indexing, ranking, and citation rendering. Each stage can store plaintext, derived text, metadata, or previews.

Embeddings are not a substitute for access control. They can encode sensitive semantics, expose document membership, and persist after the source file is deleted unless index lifecycle is explicit.

Failure points

Browser, Device, and Extension Exposure

The browser is often the first privacy boundary. Local storage, sync services, clipboard history, screenshots, extension permissions, and device monitoring can all observe sensitive content before a server ever sees it.

Client-side controls should minimize what is stored, show what leaves the device, and avoid assuming that local processing automatically means private processing.

Failure points

Network, Identity, and Metadata

DNS lookups, IP addresses, request timing, account ids, tenant metadata, model names, document names, and billing events can reveal intent even when payload content is protected.

Better systems separate identity from content where possible, minimize analytics joins, and make metadata retention explicit.

Failure points

Logging, Observability, and Analytics

Logs, traces, metrics, session replay, and support tooling are built to make systems understandable. AI workloads often place sensitive content exactly where debugging tools want detail.

Strong operations programs use redaction before telemetry, role-scoped access, retention limits, immutable access records, and evidence for support actions.

Control layers

Model Hosting, GPUs, and Compute Operators

The compute operator controls the environment that serves the model. Placement, tenancy, accelerator access, memory handling, crash dumps, and provider telemetry all shape what can be observed.

Reviewers should ask what evidence identifies the hosting environment, model family, active privacy policy, and retention posture for a specific request.

Control layers

Hardware and Software Privacy Layers

Trusted execution environments, measured boot, secure enclaves, HSMs, TPMs, and accelerator isolation can reduce operator visibility and produce useful evidence. They do not automatically solve client leakage, tool leakage, storage retention, or support access.

Software policy, key custody, network boundaries, and operational records have to line up with the hardware story for a privacy claim to be meaningful.

Verification

Verification Artifacts and Audit Records

Stronger systems preserve enough context to show which policy, model family, retention posture, timestamp, and review result applied to a request.

The best evidence is narrow and useful: it tells a reviewer exactly what was controlled, what was not claimed, and which independent checks are available.

Verification

Vendor Procurement Checklist

Start with a data-flow diagram, then ask which systems see plaintext, which systems retain content, which subprocessors are involved, which employees can access records, and which records show the stated controls were followed.

A mature vendor can explain claim scope clearly. The answer should distinguish product policy, software controls, hardware boundaries, logging behavior, key custody, and review evidence.

Control layers and evidence

Strong privacy language separates the control from the evidence that the control operated.

Software policy
Admission rules, model allowlists, tool permissions, retention limits, redaction paths, and routing controls.Evidence: policy record, approval record, and control summary.
Compute placement
Where the model executes, who operates it, which tenant boundary applies, and what telemetry exists.Evidence: hosting description, model family, operating boundary, and location category.
Hardware boundary
What is measured, where sensitive material can exist, and what remains outside the protected environment.Evidence: measurement description, review result, and exclusion notes.
Tool governance
Which tools can run, what data they can receive, and where external systems log arguments or outputs.Evidence: tool allowlist, approval event, data-sharing category, and execution status.
Telemetry minimization
How logs, traces, analytics, support exports, and crash reports avoid sensitive content by default.Evidence: log policy, retention posture, redaction result, and access record.
Verification record
How a reviewer checks the policy, model family, retention posture, and claim scope after completion.Evidence: request record, evidence summary, review result, and claim label.

Terminology

Plaintext exposure
Any point where sensitive content exists in readable form for software, operators, logs, or external tools.
Retention
The period and surface where content, metadata, derived records, or backups remain after a request completes.
Tool boundary
The approval, execution, logging, and vendor surface around an agent action outside the core model call.
Attestation
Evidence that a measured environment or hardware-backed environment matched an expected state at a point in time.
Content reference
A privacy-preserving reference to content or configuration that can support later review without exposing the original sensitive material by default.
Claim boundary
The exact scope of what a privacy statement covers, what evidence supports it, and what it does not cover.
